# myRAG 白话说明：应用场景、实现方式、和 Agent-T 的关系

> 写给：Arthur（产品定位 / 需求分析用）  
> 风格：通俗、小白、类比  
> 日期：2026-09-11  
> 目的：搞清楚 **RAG 是干什么的、什么时候用、怎么做、要不要独立成 myRAG**

---

## 0. 先用一句话记住

**RAG = 先去资料库里翻出相关原文，再让大模型对着这些原文说话。**

- 没有 RAG：大模型主要靠「自己脑子里背过的东西」+「你这次贴进去的那份合同」  
- 有了 RAG：大模型还能临时去翻「公司模板、法规、历史案例、项目附件」

类比：

| | 生活 | 合同审查 |
|---|---|---|
| 不靠库 | 闭卷考试，只靠脑子 + 眼前这张卷子 | Agent-T 现在：清单 + 当前合同 + LLM |
| 靠库（RAG） | 开卷考试，可以带参考书，但要标明抄自哪一页 | 审合同时能引用模板第 X 条、法规第 Y 条 |

---

## 1. RAG 到底解决什么痛？

大模型有三个常见毛病：

1. **会编**：没见过的公司内部规定，它可能瞎编一条「看起来很像」的  
2. **记不住你家的东西**：模型训练时没吃过你们的 NDA 范本、采购红线  
3. **一次塞不下**：项目里 20 份附件，全贴进提示词会爆、贵、慢

RAG 的作用不是「让模型更聪明」，而是：

> **把「该看的原文」准确塞到模型眼前，并尽量带来源。**

再类比一次：

- LLM = 很会写总结的实习生  
- 规则清单（Agent-T）= 考试评分标准（谁过谁挂由标准说了算）  
- RAG = 图书管理员：按问题把相关书页抽出来给实习生看  
- 实习生仍然**不能私自改评分标准**——这就是你们 Design B：「规则门禁，RAG/LLM 只提供参考」

## 2. 应用场景：什么时候真需要 RAG？

按「像不像 Agent-T」从近到远排。

### 场景 A｜现在 Agent-T（多数情况 **不需要** RAG）

- 上传**一份**合同  
- 按固定清单挑「需关注」  
- 对某条点「问清楚一点」用人话解释  

这时资料就在眼前这一份文件里。你们已经有的 **条款索引**（把合同切成「第 1 条、第 2 条」）就够用了。  
那是「**读当前这篇作文的目录**」，不是「去图书馆」。

**结论：单文档审查 MVP，不要为了 RAG 而 RAG。**

---

### 场景 B｜模板对照（**很需要**轻量知识库）

用户心里话：

> 「对方改的这版，和我们公司标准 NDA 差在哪？」

需要事先入库的东西：

- 公司标准合同模板  
- 「不可接受改法」示例  
- 条款级金标 / 红线说明  

这时 RAG（或更简单的「模板 diff + 条款检索」）开始值钱。

类比：拿**标准答卷**去对考生答卷，不是闭卷空想。

---

### 场景 C｜法规 / 制度引用（**需要**，且必须能溯源）

用户心里话：

> 「你说这条有风险，依据是哪条法规 / 哪条内控制度？」

入库：

- 常用法条摘要（或全文）  
- 公司合同管理制度、授权手册  

要求：**每一句参考必须能点回原文位置**（出处）。  
没有出处的「AI 说法」，法务不买账。

类比：法庭上出示证据，要附页码，不能只说「我觉得违法」。

---

### 场景 D｜多合同项目 / 历史案例（**需要**项目级检索）

用户心里话：

> 「这个供应商去年那份合同里违约金怎么写的？」  
> 「这个项目的补充协议、附件报价，和主合同有没有打架？」

入库：

- 同一项目下的多份文档  
- 脱敏后的历史审查案例  

类比：从「审一张卷」变成「审一整书包」，要先会翻书包找相关页。

---

### 场景 E｜对内问答 / 对外 API（RAG 做底座，审查做产品）

- 业务同学问：「我们 NDA 保密期默认几年？」→ 更像 **知识库问答**  
- 别的系统只调「审查接口」→ Agent-T 是产品；RAG 藏在后面  

类比：前台是「体检中心」，库房是「化验室」——病人找体检中心，不直接进化验室。

---

### 一张表记牢

| 场景 | 要不要独立 RAG | 一句话 |
|---|---|---|
| 单份合同 + 清单审查 | 否 | 桌上有卷子就够 |
| 追问「这段什么意思」 | 否（文档内上下文即可） | 读眼前这一段 |
| 对标准模板 / 红线库 | 要（可先做薄） | 开卷对标准答 |
| 引用法规 / 内控 | 要 + 强出处 | 证据链 |
| 多文档项目 / 历史案例 | 要 | 翻书包 |
| 纯公司知识问答 | 要（甚至可先独立产品） | 图书馆咨询台 |

## 3. RAG 实现长什么样？（流水线五步）

别被术语吓到。做成产品，通常就五步：

```
资料进馆 → 切碎 → 做成「可搜索卡片」→ 按问题找出相关卡片 → 把卡片塞给大模型写答案
```

### ① 资料进馆（Ingest）

把 Word/PDF/Markdown 变成纯文本。  
难点在扫描件、表格、双栏 PDF——这就是为什么有人爱用 **RAGFlow**（解析强）。

类比：新书盖章入库。

### ② 切碎（Chunk）

太长一次搜不准，所以切成小段（按条款、按标题、按大约几百字）。  
合同场景**优先按「条款」切**，比「固定 500 字一切」更合理。

类比：把厚书拆成便利贴，每张写清「出自第几条」。

### ③ 做成可搜索卡片（Index）

常见两种：

- **关键词检索**：像 Ctrl+F / 搜「违约金」（传统搜索）  
- **向量检索**：按「意思相近」找（语义搜索）——把文字变成一串数字，比「像不像」  

也可以 **两者混合**（很多产品默认这样）。

存这些卡片的地方叫向量库 / 搜索引擎（Milvus、Qdrant、Elastic 等）。  
小白阶段：**你不必先自建库**，用成熟套件自带的即可。

### ④ 按问题找卡片（Retrieve）

用户或 Agent 问：「付款条件有没有对我方不利？」  
系统返回 Top-K 段原文 + 来源。

类比：图书管理员递过来 5 张贴了页码的复印件。

### ⑤ 让模型对着卡片说话（Generate）

提示词大意：

> 只能根据下列摘录回答；没有就说「资料里没找到」；每句带出处。

类比：实习生必须指着复印件发言，不许凭空编。

**和 Agent-T 铁律对齐：**

- RAG 产出 = **参考材料 / 候选关注点**  
- 清单规则 = **最终标签**（通过 / 需关注 / N/A / 未找到）  
- Copilot = **解释与改写**，不盖「没问题」章

## 4. 开发方式：三条路，怎么选？

### 路 1｜整套开箱产品（适合「先跑通场景」）

代表：**Dify**、**RAGFlow**

| | Dify | RAGFlow |
|---|---|---|
| 像什么 | 带装修的店面 + 后厨 | 特别会拆书、做摘录的专业图书馆 |
| 强项 | 可视化编排、应用/Agent、上手快 | PDF/表格解析、引用质量 |
| 弱项 | 超难版式文档可能一般 | 不如 Dify「产品壳」那么全能 |
| 许可注意 | 开源可用，多租户 SaaS 等有附加条款，上线前看法务 | Apache-2.0，相对清爽 |

**适合**：验证「模板库问答」「法规引用」值不值得做；非核心团队少写胶水代码。

### 路 2｜检索库 + 自己写一点胶水（适合「已确定要嵌进 Agent-T」）

用 LangChain / LlamaIndex 等库：

- 自己控制切块、提示词、和审查流程的衔接  
- 工作量大，灵活度高  

**适合**：已经清楚接口长什么样，要深度嵌进审查编排。

### 路 3｜先不做向量，做「薄知识层」（很多合同产品其实从这起步）

例如：

- 模板全文 + 条款级人工标签  
- 规则 YAML 里挂「参考范文片段」  
- 简单关键词检索历史案例  

**适合**：阶段 2～阶段 3 早期——先证明「对照模板」有人用，再上重型 RAG。

## 5. 推荐产品定位（给需求分析用）

### 5.1 两个产品的分工

**Agent-T（审查产品）**

- 负责：上传、清单、立场、证据链、报告、追问解释  
- 用户感知：「帮我审这份合同」  
- 核心指标：准、可对质、不乱盖章  

**myRAG（知识与检索底座，可选）**

- 负责：模板库、法规/制度库、项目文档库、带出处的检索  
- 用户感知：多数时候**无感**（藏在 Agent-T 后面）；也可单独做「制度问答」小入口  
- 核心指标：找得准、引得出处、更新资料不求开发改代码  

一句话：

> **Agent-T 是体检报告；myRAG 是化验设备。**  
> 没有化验设备也能做基础问诊（规则清单）；要做深度体检再接化验。

### 5.2 接口先定、实现可换（防绑死）

对 Agent-T 只暴露一个薄接口，例如：

```text
retrieve(
  query: 问题或条款摘要,
  scope: 模板库 | 法规库 | 本项目文档,
  top_k: 几段
) → [
  { text, source_id, title, locator }  // locator=页码/条款号
]
```

背后今天可以是 Dify，明天可以是 RAGFlow，后天可以是自研——**审查主流程不改**。

### 5.3 需求优先级（建议）

| 优先级 | 需求 | 验收（小白版） |
|---|---|---|
| P0 | 单文档审查不依赖 RAG | 关掉 myRAG，Agent-T 演示仍完整 |
| P1 | 模板库检索 + 出处 | 问「和标准 NDA 保密期差异」，能指出模板条款号 |
| P1 | 检索结果不得改写规则结论 | 规则标「通过」时，RAG 只能当参考提示，不能擅自改成「需关注」覆盖规则（或仅允许「候选补盲」且可关） |
| P2 | 法规/制度引用 | 每条参考可点开原文 |
| P2 | 项目多文档检索 | 指定项目范围内搜附件 |
| P3 | 独立「知识问答」入口 | 不审合同也能问制度 |
| P3 | 管理后台：上传/下架资料、权限 | 法务自己更新库，不找开发 |

### 5.4 明确不做（护栏）

- 不把「向量库」当成审查正确性的保证  
- 不用 RAG 替代金标 / 红线 / 清单门禁  
- 不把密钥、未脱敏真实合同随便进共享库  
- 不做「为了技术选型而先造平台」——场景验证优先

## 6. 建议落地顺序（和扩展对齐）

```text
现在     ：Agent-T 继续单文档（规则 + LLM），不强制 myRAG
近未来   ：用 Dify 或 RAGFlow 做一个「标准 NDA/采购模板库」试验场
验证有用 ：再把 retrieve() 接到 Agent-T「模板对照 / 参考依据」入口
再往后   ：项目多文档、法规库、权限与更新流程
```

选型经验法则（结合你们之前调研）：

- 想**快验证产品壳 + 工作流**：优先试 **Dify**  
- 想**难文档解析 + 引用质量**：优先试 **RAGFlow**  
- 两者都可先 Docker 起一个玩，**先别深度耦合进 Agent-T 主仓**

## 7. 给你开会用的 30 秒版

1. RAG = 开卷考试：先翻书，再答题，并标明页码。  
2. Agent-T 现在是闭卷审单份合同，**不必须** RAG。  
3. 要对标「模板对照、法规引用、多合同项目」，**才值得**独立 myRAG。  
4. myRAG 是底座服务，Agent-T 是审查产品；规则仍说了算。  
5. 开发上：先开箱产品验证场景 → 定 `retrieve` 接口 → 再决定深嵌或自研。

## 8. 名词小词典（怕忘就看这）

| 词 | 人话 |
|---|---|
| RAG | 检索增强生成：先找资料再生成回答 |
| Chunk | 切碎后的一小段资料 |
| Embedding / 向量 | 把文字变成数字指纹，方便找「意思相近」 |
| 向量库 | 专门存这些数字指纹的仓库 |
| 引用 / Citation | 答案对应的原文出处 |
| 幻觉 | 模型一本正经瞎编 |
| 知识库 | 你允许系统去翻的那批资料 |
